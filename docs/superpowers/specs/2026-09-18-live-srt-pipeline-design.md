# Live SRT Contribution-to-Distribution Pipeline on AWS: Design

Date: 2026-09-18
Status: Draft for review

This document has two parts: a product part (PRD: what and why) and a technical part (TRD: how). A README is written after implementation.

# Part 1: PRD

## Purpose
A portfolio project, published as a Medium article and a GitHub repo, that demonstrates managing live broadcast cloud infrastructure with Terraform on AWS. It targets a Broadcast Cloud Engineer role (live sports host broadcast: SRT, AWS media services, Python automation, monitoring).

## Audience
Hiring managers and engineers in live broadcast and cloud infrastructure.

## Goals
1. Show a "stadium to screen" live path: SRT contribution in, ABR HLS distribution out.
2. Show infrastructure as code done properly: modules, remote state, tests, tagging, conventions.
3. Show Python automation for operating the workflow (start, stop, status, clean-check).
4. Show cost awareness: budget guardrails, short-lived demos, honest cost estimate.
5. Provide a concrete latency demonstration in the player.

## Success criteria
- `terraform apply` from a clean account state produces a working pipeline.
- An FFmpeg SRT source connects, and the stream plays in the hosted player page.
- The player shows the burn-in timecode next to the viewer's clock.
- `stop` and `terraform destroy` leave nothing billable running, confirmed by `check-clean`.
- `terraform test` passes without AWS credentials.
- Total spend for development and demos stays within the $25 budget.

## Out of scope (v1)
- Redundant (dual-pipeline) operation. The channel class is a variable, but the demo uses single pipeline.
- Monitoring, alarms and auto-remediation (candidate project #2).
- Multiple environments, CI pipelines, ad insertion, DRM, web UI.

## Constraints
- Personal AWS account, self-funded, $25 budget cap.
- Region: us-east-1 (chosen for cost and service availability).
- Author is new to Terraform and FFmpeg, comfortable with Python and prior SRT use.

# Part 2: TRD

## Architecture

```
FFmpeg (test pattern + burn-in wall-clock timecode)
   │  SRT caller, passphrase-encrypted
   ▼
MediaConnect flow (SRT listener, CIDR-whitelisted)
   ▼
MediaLive channel (single pipeline, ABR ladder 1080p/720p/480p)
   │  HLS
   ▼
MediaPackage (channel + HLS endpoint)
   ▼
CloudFront ──► static player page (S3 + CloudFront OAC, hls.js + latency overlay)
```

### Key decisions
- **MediaConnect as the ingest layer** (rather than SRT directly into MediaLive). It is the standard contribution-transport pattern and leaves room for extra outputs or a second source later. Direct SRT into MediaLive is documented in the article as a cheaper alternative.
- **MediaConnect is provisioned with the `awscc` provider** (`awscc_mediaconnect_flow`), because the `hashicorp/aws` provider has no MediaConnect flow resource. Everything else uses `hashicorp/aws`. The `ingest` module is the only one that uses `awscc`. If a spike shows `awscc` cannot create, connect and destroy the flow cleanly, the fallback is a `terraform_data` resource calling the AWS CLI.
- **MediaPackage v1** (`aws_media_package_channel`, HLS), because `aws_medialive_channel` only supports the v1 HLS output in the provider. v2 is documented as a known gap.
- **Channel class is a variable**, defaulting to `SINGLE_PIPELINE`. The class is immutable after channel creation, so changing it replaces the channel. `STANDARD` also requires a second input and destination, and is not exercised in v1.
- **Ingest security:** SRT passphrase generated by Terraform and stored in Secrets Manager. The listener accepts only a configured source CIDR. The passphrase also lands in Terraform state, which is a known trade-off mitigated by a private, encrypted, versioned state bucket.
- **Delivery:** CloudFront fronts MediaPackage so the packager is not publicly open. The player page is served from a private S3 bucket via CloudFront OAC.
- **Latency overlay:** the page compares the burn-in wall-clock time with the browser clock. It is approximate (clock skew) and is presented as a demonstration, not a measurement.

## Repository layout

```
live-sports-aws/
├── bootstrap/        # one-time: S3 state bucket (local state)
├── modules/
│   ├── ingest/       # MediaConnect flow, SRT passphrase secret, CIDR whitelist
│   ├── encode/       # MediaLive input, channel, IAM role, channel_class variable
│   ├── package/      # MediaPackage channel + HLS endpoint
│   ├── delivery/     # CloudFront distribution, OAC
│   ├── player/       # S3 bucket + static page (hls.js + overlay)
│   └── guardrails/   # AWS Budgets + alerts
├── envs/demo/        # wires modules; variables; backend config
├── tools/            # Python CLI
├── source/           # FFmpeg script
├── tests/            # .tftest.hcl per module
└── README.md
```

Each module has `main.tf`, `variables.tf`, `outputs.tf` and `versions.tf`, follows the terraform-style-guide skill, pins provider versions, and applies consistent tags (`Project`, `Env`). Only the `demo` environment exists.

Module contracts: `ingest` outputs the flow ARN and SRT endpoint; `encode` consumes the flow and outputs the channel ID and packaging destination; `package` outputs the HLS endpoint; `delivery` outputs the distribution domain; `player` consumes that domain.

## State
Remote state in an S3 bucket (versioning, encryption, public access blocked) created by `bootstrap/`. Locking uses S3 native lockfile (`use_lockfile`), so no DynamoDB table is needed.

## Python tooling (`tools/`)
A CLI using `boto3` and `argparse`, with no framework. Resource IDs come from `terraform output -json`; nothing is hardcoded.
- `start`: starts the MediaConnect flow, then the MediaLive channel, waiting for each to be running.
- `stop`: stops the channel, then the flow, waiting for both to be idle.
- `status`: prints flow and channel state, whether the SRT source is connected, the SRT endpoint and the playback URL.
- `check-clean`: confirms nothing billable is still running after `destroy`.

Tests use `pytest`, with `moto` if it covers the MediaLive and MediaConnect APIs, otherwise stubbed clients.

## FFmpeg source (`source/`)
A commented shell script wrapping one FFmpeg command: `testsrc2` plus tone, burned-in wall-clock time via `drawtext`, H.264/AAC, pushed over SRT with the passphrase and a configurable `latency`. Endpoint and passphrase come from environment variables.

## Testing
- `terraform fmt -check` and `terraform validate` on every module.
- `terraform test` with `.tftest.hcl` files, `command = plan` and mocked providers: channel class variable and validation, CIDR validation, tag propagation, module wiring. No AWS credentials needed.
- Python: `pytest` as above.
- End-to-end verification is the live demo itself.

## Cost controls
- AWS Budgets: $25 monthly, alerts at 50% and 80% (actual) and 100% (forecast), by email. Alerts lag, so they are a safety net.
- Primary control is behavioural: `stop` and `terraform destroy` after each session, verified by `check-clean`.
- The cost estimate in the article is computed from current AWS pricing pages and labelled as an estimate.

## Demo flow
`terraform apply` → `tools start` → run FFmpeg script → open player page → `tools stop` → `terraform destroy` → `check-clean`.

## Risks

| Risk | Mitigation |
|---|---|
| `awscc` MediaConnect quirks (a reported apply that never finishes) | Spike first; CLI fallback |
| Forgotten running channel | Budget alerts, `check-clean`, destroy after every session |
| SRT connection issues (latency, firewall, passphrase) | Documented FFmpeg flags; `status` shows input connection state |
| Approximate latency overlay | Stated plainly in the article |
| Channel class immutable | Documented in the module |
| Passphrase in state | Private, encrypted, versioned state bucket; noted as trade-off |
